Google Docs System Design: How Operational Transformation Survives Millions of Concurrent Editors

Two cursors land in the same sentence at the same millisecond. Nobody refreshes. Nobody merges. Nobody loses a paragraph. This teardown explains the ordering machine behind that trick and what the ordering costs at scale.

TL;DR: Docs merges edits with central OT ordering and per-document serialization. Presence stays ephemeral while ops stay durable. Snapshots bound replay cost.

1. The Moment Typing Became A Distributed System

Most products can queue writes politely. A word processor cannot. When a lawyer types a comma, the comma must appear now, not after consensus across three zones. When a second lawyer deletes the same sentence, both screens must converge without a merge dialog. When the train tunnel eats the network, the offline paragraphs must rejoin the document without duplicating the exhibit list.

Docs is therefore an ordering system wearing a toolbar. Clients hold a local copy and apply edits instantly. Every edit becomes a small op: insert text at a position and delete a range and retain formatting across a span. Ops travel over a persistent connection to the owner process for that document. The owner assigns a revision number and broadcasts the accepted op to every witness.

The hard question is positional drift. An op authored against revision 41 may arrive after revision 44 has committed three inserts before its target index. Applied literally, the op lands in the wrong paragraph. Operational Transformation rewrites the late op so its intent survives the new history. That rewrite is the whole product.

The working picture: one ledger and a single pen. Clients draft optimistically. The owner sequences every entry. The broadcast is the statement everyone reads at once.

2. Why Docs Beats Another Chat Clone As An Autopsy

Chat systems route blobs and delete them after delivery. Docs must preserve intent and history and undo across years of edits from strangers sharing one paragraph. The constraints are stricter so the lessons travel further.

The paper trail helps. Google shipped Wave in 2009 on OT and retired the product while keeping the engine. The Jupiter system formalized the client revision model. The Drive team then published a three-part collaboration series describing optimistic clients and server ordering and revision logs. Few realtime products document their conflict core this openly.

The contrast with Figma sharpens the lesson. Figma multiplayer chose server-authoritative property resolution for spatial objects where last-writer-wins stays legible. Docs edits prose where character interleaving must preserve both authors. Same realtime family. Opposite conflict math. The bill hides in the boundary between the two choices.

3. The Architecture: One Document and One Owner and Many Witnesses

Open a document and your browser downloads a snapshot and opens a persistent connection. A routing layer pins every connection for that document to its owner process using consistent hashing on the document identifier. Two unrelated documents never share an ordering lock. One overloaded thesis cannot stall a stranger boarding pass.

The owner holds live state and the revision counter. Edge gateways terminate sockets and authenticate and forward. Product data such as permissions and comments and Drive metadata lives outside the OT path in transactional stores and a search index. That split keeps a slow comment thread from freezing keystrokes.

Durability sits behind speed. The owner appends every accepted op to an append-only revision log before broadcast fans out. Periodic snapshots capture full state roughly every 30 ops in this scenario. Recovery loads the newest snapshot and replays only the tail. History and undo and offline catch-up all ride the same log.

Architecture tip: separate state by durability need. Ops need ordered persistence. Cursors need fast forgetting. Snapshots need cheap reads. One magic realtime store serving all three becomes a 3 a.m. pager with a toolbar.

4. The Transform Core: How Two Edits Stop Erasing Each Other

Consider the canonical collision. Ana inserts X at position 5 against revision 41. Ben deletes the character at position 3 against the same revision. The server commits Ana first as revision 42. Ben op arrives late. Applied literally, Ben deletion points at the wrong character because Ana insert shifted every index after position 5.

The transform function repairs it. Transform takes two ops authored against one base state and returns adjusted forms that compose in either order while preserving intent. Ben delete at 3 stays valid. A later insert authored at 5 after a prior delete at 3 shifts left by one. Overlapping deletes collapse to a no-op for the already removed range. Inserts at the same index tie-break deterministically by author and session order so every replica picks the same winner.

Jupiter discipline makes this tractable. Each client tracks its last synced revision and a buffer of sent-but-unacked ops and a buffer of unsent local edits. The server transforms each arrival against every commit since the sender last revision. Clients transform pending buffers against each broadcast. Periodic text checksums force a resync when a replica drifts. Central order and linear history and checksums. That trio carries the correctness load.

Interview line: name the three buffers and the revision number. Optimistic apply buys latency. Server order buys convergence. Checksums buy honesty when transforms hide a bug.

5. The Transform Matrix: Which Op Pairs Actually Collide

Transform looks like one function. In production it is a matrix of op-pair cases, and the matrix is where convergence bugs hide. Plain text pairs are the easy rows. Rich pairs carry the risk.

Walk the common rows. insert against insert at one index: both survive in a deterministic order fixed by author and session tie-break, so every replica picks the same winner. insert against delete: the insert index shifts past the removed range. delete against delete: overlap collapses and the second op shrinks to the surviving range or becomes a no-op when its target already vanished. Formatting span against delete: the span shrinks to the surviving characters instead of dangling across removed text.

The literature names the deeper properties TP1 and TP2: pairwise convergence and path independence across three or more concurrent ops. Proving both for rich text is genuinely hard, and published OT algorithms have failed on specific interleavings in the past. The central linear history is the practical escape: the server reduces every many-way tangle to a sequence of pairwise transforms against one ordered log. Peer meshes face the full property. A pinned owner faces it one op at a time.

Testing tip: fuzz op pairs, not just single ops. Generate random concurrent pairs across inserts and deletes and spans, apply them in both orders and compare checksums. Order-swapped divergence is the cheapest convergence oracle ever built.

6. OT Against CRDT: Why Docs Kept The Server

CRDT designs remove the transform by giving every character a stable sortable identifier and tombstoning deletes. Replicas merge in any order with no central rewrite. Libraries like Yjs and Automerge prove the model daily. Notion leans on this family for offline-first block merging where peer convergence matters more than wire size.

Docs kept OT for three priced reasons. First, ops stay tiny: position and payload versus identifier and causal context per character. At billions of keystrokes, bytes become budget. Second, a server already exists for auth, storage, and search, so central ordering costs nothing extra while removing an entire class of transform proof burden. Third, tombstones accumulate: heavily edited long-lived documents carry many times their visible size until garbage collection, a tax OT never pays.

The rule transfers cleanly. Central server and rich text and always-online adjudication favors OT. Decentralized and offline-first and peer merge favors CRDT. Figma picked a third shape because canvas objects tolerate property resolution while prose cannot. Choose by product invariant, never by conference fashion.

7. The RPS Model: How Much Traffic Does Typing Make

Google does not publish a per-keystroke histogram, so the following is a scenario with explicit assumptions. Assume 300 million monthly editors and 8 million concurrent sessions at a busy peak. Assume each active session produces 30 ops per minute including typing bursts and formatting and suggestion threads. That yields 4 million durable ops per second before fan-out.

Presence dwarfs edits. Assume 8 million concurrent sessions each emit throttled cursor and selection frames at 2 per second after client coalescing. That is 16 million ephemeral frames per second. Snapshot and log writes add a smaller durable tail: one snapshot per 30 ops across 400 thousand hot documents produces roughly 130 thousand snapshot writes per minute and log appends equal to op rate.

8. What This Ordering Machine Might Cost

Cost the scenario as regional infrastructure: edge and owner fleet and log and snapshot stores. Suppose 600 edge and owner workers average 0.55 per hour after commitments and connection proxies and control services. Compute lands near 240 thousand per month. Add cross-zone transfer and load balancing and observability and failover headroom: 180 thousand to 320 thousand per month.

Transform workers need memory for hot documents. Assume 400 thousand hot documents at 25 MB resident OT state and buffers and replica overhead. That is 10 TB logical before replication. With three-way replication and spare pools, managed memory and compute envelope lands near 140 thousand to 260 thousand per month.

The revision log and snapshots and product data complete the ledger. Assume 2 PB of op history with lifecycle trimming and 800 TB of snapshots and Drive metadata and permissions and search indexing. Storage and transfer and indexing envelope lands near 160 thousand to 330 thousand per month. Combined, the collaboration platform in this scenario lands near 480 thousand to 910 thousand per month, roughly 16 thousand to 30 thousand per day.

9. The One Million RPS Thought Experiment

Treat one million durable ops per second as a stress lens, not a Google disclosure. Assume each op carries 0.5 KB inbound and 1 KB outbound and three persisted copies across routing and processing and failover. The wire carries roughly 4.5M KB per second. Over a 30-day month, that is about 11.7 PB of logical movement before compression.

Take the unoptimized shape first: assume a fully loaded origin cost of 0.0000012 per op including transform and log append and fan-out. The math is 1,000,000 x 2,592,000 x 0.0000012 = 3.11M per month. This covers owners and revision log and cross-zone fan-out and metrics and spare headroom.

The proposed shape separates lanes. Coalesce typing bursts at the client and route presence through a lossy relay and serve reads from snapshots and edge caches and send only canonical ops to the owner. If origin traffic falls to 40 percent at 0.0000008 per op, origin work is 400,000 x 2,592,000 x 0.0000008 = 829k per month. Add 260k for relays and caches and observability and headroom. The proposed envelope totals near 1.09M per month, about 65 percent below the unoptimized shape.

The takeaway for a million ops per second: lane separation decides the invoice, language choice only prices the remainder.

10. How I Would Cut The Bill Without Losing Convergence

1. Treat presence as disposable. Cursors and selections and viewport hints ride a best-effort relay with 10 Hz caps and coalescing and no persistence. Never append a cursor to the revision log. A dropped cursor is invisible. A journaled cursor is a storage annuity.

2. Pin documents near their dominant editors. One owner per document simplifies order but punishes intercontinental sessions when the owner sits on the wrong ocean. Place owners near the heaviest editor cluster and proxy the rest. Migrate only when measured round-trip savings beat handoff complexity.

3. Coalesce bursts before they become history. Typing arrives in bursts. Merge intra-word keystrokes within short windows into compact ops before transform and persistence. Keep semantic undo granularity while refusing to immortalize every inter-key interval.

4. Tune snapshot cadence by edit velocity. Hot documents earn frequent snapshots to bound replay. Cold documents keep sparse snapshots and deep logs. Snapshot policy should follow measured ops per minute, never a global constant inherited from a calmer era.

5. Isolate hot documents automatically. One viral planning doc with hundreds of witnesses must never share an owner with thousands of quiet memos. Detect queue depth and transform latency and broadcast backlog. Route outliers to isolated owners without human triage.

6. Buy commitments for the floor and spot for the broom. Owners and edge and log writes are the floor. Reindexing and export rendering and historical compaction are the broom. Commit to the floor. Interrupt the broom. A compaction that cannot survive preemption is a hostage note, not a job.

7. Verify convergence with checksums, not hope. Clients send cheap text hashes with revision markers. The server compares and forces resync on mismatch. Transform code stays small and honest because an independent check watches every merge.

Optimization tip: track dollars per million durable ops and dollars per million presence frames and dollars per GB of revision history per month. Blended cost per user hides whether the invoice comes from writing or from watching cursors dance.

Notice the pattern. Every recovery reads from the same two artifacts: the newest snapshot and the ordered tail. The log is not just durability. 12. The Postmortem Verdict

Docs endures because it refuses to solve the general collaboration problem. It solves text with a central order and tiny ops and an honest log. No peer mesh. No universal CRDT. No journaled cursors. The constraints look narrow until a million people type at once, at which point narrow is the only shape that fits through the door.

Steal the owner rule first. One serializer per document keeps agreement off the hot path. Steal the lane split next. Ephemeral presence must never touch durable storage. Steal the snapshot discipline last. History is a product feature with a storage price, so price the cadence explicitly.

The canvas at Figma feels simple because a server settles property fights elsewhere. The page at Docs feels simple because a server rewrites late ops before witnesses see them. Different conflict math. Shared discipline: name the line between durable and disposable in code, because production bills whatever you leave unnamed.

Everyone types at once because one process decides the order and proves it with a log.

Frequently Asked Questions

How does Google Docs collaboration work?

Browser clients apply edits optimistically and send small ops over a persistent connection to the owner process holding their document. The server orders ops authoritatively and broadcasts transformed ops to every connected client.

Does Google Docs use OT or CRDT?

Google Docs uses Operational Transformation with a central server that assigns revision order. CRDT libraries like Yjs power newer tools such as Notion and Linear where offline-first merging matters more.

Why did Docs keep OT instead of switching to CRDT?

OT keeps ops tiny and needs no per-character metadata. A central owner already exists for ordering so the transform stays tractable while CRDT tombstones would tax every long-lived document.

How does Docs handle offline edits?

The client buffers ops against its last synced revision. On reconnect the server transforms queued ops against everything committed during the outage and replays missed ops from the revision log.
